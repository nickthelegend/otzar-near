# Otzar full-flow QA — 2026-11-11

Scope: production build, real NEAR testnet reads, headless installed Chrome at 1440×1000 and 375×900. Functional fixes only; approved typography, colors, layout and art stay unchanged. Wallet approval requires a human Meteor account; scripts verify the on-chain paths within a 0.3 NEAR QA budget. No mainnet writes.

## Ordered judge flow

1. Install dependencies, build the SDK and web app, and serve the app using README Try it.
2. `/`: read the pitch, live testnet round totals, earning-vault table and actual on-chain activity. Follow navigation and footer links.
3. `/how`: read the trade-off, real round, safety limits and NEAR integration table. Open every FAQ; follow the safety anchor; try the exposure scanner's validation, live public read and local-only sweep boundary.
4. `/app` (also `/vaults`): inspect the APY chart and round drawer; switch Earning / All / Yours; follow a vault row. Exercise the disconnected/empty states.
5. `/vault/<id>`: inspect the latest-round sentence, strike bar and timeline. Open/close Details by its button, Escape and scrim. Inspect an exercised ITM vault, a released OTM vault, a vault without rounds, a missing vault and malformed route input.
6. Connect: open Meteor Wallet on testnet for `hako-contract-mw984kpp.testnet`; verify closed and blocked popup feedback. Human approval/account creation is not automated.
7. Main owner path after real sign-in: New vault → mint → generate/register ML-DSA key → register Bitcoin rules → fund local regtest address → write covered call. Main buyer path: buy with tUSDC → writer receives premium → settlement → strike payment and MPC exercise, or OTM release. Verify these contract call paths using the repo's existing demo script and actual receipts.
8. Vault result/controls: Deposit and Withdraw; strategy and Safety locks disclosures; Owner tools Overview / Rules / Send ETH / Send BTC / Send SOL / Rounds / Recovery / Sell. Inspect read-only gates and all forms reachable without impersonating a wallet.
9. `/you`: disconnected portfolio prompt; after human sign-in, token balance, vaults, rounds, activity and sign-out. Browser-authenticated owner/position views remain explicitly blocked until a human signs in; contract paths are checked separately.
10. Other states: network failure and Retry, no vaults/no rounds, missing contract setup, invalid scanner input, invalid IDs and reload/back/forward/hash navigation. Fault-injected states are identified separately from live data.

## Live contract and local-chain verification

The earlier full-flow QA sent **31 NEAR testnet transactions**: 26 succeeded and five security checks were rejected as intended. It spent a conservative **0.2148811182476367 NEAR**, including net added storage and an extra count of the 0.001 NEAR internal sale payment. The browser run shares the same 0.3 NEAR cumulative cap.

- [Covered-call loop](deployments/calls-live-testnet-2026-11-11-152019.json): 19 transactions; writer received 0.019313 tUSDC; two encumbered BTC spends rejected; ITM buyer received 10,000,000 sats on regtest; OTM writer received 10,009,000 sats back. Both new Bitcoin receipts were re-queried and confirmed.
- [Empty NFT sale and expired-auction close](deployments/flow-qa-2026-11-11.json): mint, list at 0.001 NEAR, buy, and close `call-mw9c9f1x`. The sale reset authority/recovery state and assigned the guardian to the new owner. The old unfilled round changed from `auction` to `unfilled` on chain.
- [Guardian recovery](deployments/recovery-2026-11-11.json): eight transactions, including insufficient guardians, early finalization and old-key rejections. Recovery succeeded after the actual two-minute delay.
- Thirty focused regression assertions passed for NEAR denominations, the contract-derived lock-state matrix, and pending/signed round narratives and timeline completion.
- Three historical Anvil receipts and the original two Bitcoin receipts were re-queried successfully. Historical NEAR replay through `scripts/verify-evidence.mjs` hit external HTTP 408; it is not counted as a new pass. The old Solana signature was absent from the restarted local validator’s status lookup, so its 2026-11-09 receipt remains archival evidence, not a freshly re-confirmed transaction.

The demo script’s saved `annualisedYieldPct` uses write-time spot notional. The web UI correctly derives yield from strike notional as README describes; these are different denominators. Premium amounts and transaction hashes are unchanged.
